# AI对话功能对齐与接口演进计划

整理日期：2026-10-23。状态：分析与推进清单，功能尚未实施。

本轮目标是吸收私人版近期已经落地的对话改进，让开源桌面版能够找回已有资料、完整读取原文、提供可核验的回答，并改善长聊天与失败恢复体验。建议先补齐资料工具和聊天可靠性，再增加来源引用与可选语义检索；Responses API 作为独立试点评估，先保留现有多服务商与本机 Codex 路径。

- 开源版 `personal-ai-secretary`：`73e5661229b7b767815bee2523b51c5fd39f2011`，版本 `0.6.0-beta.2`。

## 分阶段推进清单

以下复选框表示在开源版中的完成情况。每项完成后记录实际提交和验证证据；先完成对应依赖，再推进下一项。

### 第一阶段 资料读取与回答质量

- [ ] **A0 记录对话阶段耗时。** 在 API 和 Codex 两条路径采用一致的阶段定义，记录首段可显示文字、工具耗时、上下文估算与成功状态；日志不记录正文、附件或凭据。后续优化用同条件样本对比，不将上下文字符减少比例当作速度提升比例。
- [ ] **A1 同步回复策略。** 把原文核实、先查后问、确认与推测的区分、简短推进做成共用规则，并让已有会话每轮收到新版本。用户当轮已经给出完整原文时可直接分析，不为获得引用而重复查询。
- [ ] **A2 增加已保存附件读取工具。** 提供目录和附件 ID 读取，支持文字分段、PDF 按页及 Word 图文。工具按会话范围检查访问权限；需要看文件时实际读取内容，不凭文件名判断。优先复用桌面已有 Node 解析能力，额外 Python 等依赖须明确打包和验证。
- [ ] **A3 改为轻量任务快照及按需读取。** 每轮提供最新状态、短预览和资料目录；全文、任务经过和单条沟通通过工具读取。预览明确长度与是否截断；正文分段携带版本，资料变更后拒绝继续混读旧版本。同一持久会话中已有的消息不反复注入，外部新增进展仍须可见。
- [ ] **A4 补齐分页和总数。** 任务等列表返回真正的 `total`、本页记录和下一页位置；筛选条件跨页保留。长字段与交易原文可以续读。精简写入回执，保留实际保存字段、记录 ID 与必要预览。保留现有财务汇总口径，不用分页列表替代正确的聚合计算。

验收条件：

1. 用户询问以前上传的合同，不重新上传也能读取；能够找到 PDF 指定页、长文末尾信息和 Word 中的相关图片。
2. 超过一页的任务能完整列出、正确计数；相同时间戳的记录不重复、不遗漏，筛选条件翻页后保持一致。
3. 资料在分段读取中途修改时，明确要求从新版本开始读取；任务外新增进展在下一轮可见。
4. 任务原始 `detail`、聊天记录、附件和既有 Codex 线程保留；当前任务的写入范围不扩大。
5. 同一问题在通用与任务对话、API 与 Codex 中分别验证；旧摘要只能作为线索，关键数字重新核对原文。

### 第二阶段 聊天体验与失败恢复

- [ ] **B1 统一持久化和失败状态。** 用户消息与附件在模型处理前可靠保存，生成失败仍可查看。错误跟随原轮次显示，不被后续成功回复覆盖；发送重试及业务写入分别去重，后台重启后不自动重放可能已执行的业务动作。沿用 Codex 已有保护并补齐 API 路径。
- [ ] **B2 增量历史及渲染优化。** 用稳定游标加载更早消息，合并增量时按 ID 去重并保留未变化对象；旧消息与 Markdown 渲染隔离。向上翻页保持阅读位置，用户正在读旧消息时不强制滚到底部。语音刷新消息时避免卸载录音或播放组件。
- [ ] **B3 统一任务输入。** 新留言与交结果共用任务 AI 浮层；历史留言、附件、未处理记录保留。收起再打开保留草稿和附件，AI 回复后刷新任务结果。发言人继续使用用户配置，不能搬入私人版的固定姓名。
- [ ] **B4 消息复制。** 用户消息、AI 已完成回复均可复制，包含成功和失败反馈；接入引用后复制完整的来源列表。流式未完成消息的可复制状态需明确定义。

验收条件：

1. 模型超时、上传后断网、重复发送及后台重启均使用隔离数据测试；已保存附件可访问，已执行的任务不会重复创建。
2. 先失败后成功的两轮记录中，原失败仍能看见。开源版提示可查看和恢复处理，不承诺有人工管家稍后接手。
3. 长聊天逐页核对数据库消息 ID；翻页不丢记录、不跳阅读位置；输入草稿不会重复解析全部旧消息。
4. 390px 与宽屏验收任务浮层、焦点恢复和复制；原任务页位置与排版保持稳定。
5. 手动录音、连续语音和实时语音继续正常工作，历史更新不使实时会话意外关闭。

### 第三阶段 引用与语义检索

- [ ] **C1 可核验资料引用。** 在 A2、A3 的成功原文读取上生成本轮来源标记，后台核对工具审计和记录存在性，生成句末编号与来源列表。目录、检索候选、读取失败及写入回执不能冒充原文引用。引用随消息持久化，支持 PDF 页码和长文位置。
- [ ] **C2 可选增量语义检索。** 完成设置界面、模型配置、发送范围说明和用户明确开启流程；默认关闭。新增、修改、删除及附件替换均使索引正确更新或失效，失败不阻塞业务保存。任务聊天默认当前任务，必要时只读参考其他符合条件的资料；关闭功能后关闭该扩展入口，写入范围保持原样。

验收条件：

1. 伪造、其他轮次、读取失败和已删除来源均不能产生有效可点击引用；未实际引用的已读资料不进入来源列表。
2. 引用指向实际读过的片段或页码；该机制不被描述为已自动证明每句推理正确。
3. 语义检索使用独立配置和用户自己的额度，发行包不带开发者密钥；不会复制私人版索引、业务数据或出站授权。
4. 对“改写问题、无答案、旧资料、冲突事实、附件替换、归档或删除、服务不可用”进行验证。命中候选后读原文；未命中不能证明资料不存在。精确金额、日期和计数仍通过结构化查询。
5. 更换模型或向量维度必须重建相应索引；旧内容或排队修订不能作为当前事实返回。

## 当前 API 与会话管理

### API 模式使用 Chat Completions

入口 [chat-agent.ts](../src/lib/chat-agent.ts) 使用 `createOpenAICompatible` 和 `provider.chatModel(cfg.model)`。本机安装的 `@ai-sdk/openai-compatible` 将该调用发送到配置的 Base URL 下的 `/chat/completions`。因此准确名称是 **Chat Completions 兼容接口**，不是旧式 `/completions` 接口，也不是当前应用直接调用 `/responses`。

浏览器主要只发送本轮消息。服务器从本机数据库按 `conversationId` 读取历史，整理为模型消息后再发送。当前 [chat-context.ts](../src/lib/chat-context.ts) 已经实现：

- 从 `Message`、`ChatSummary` 拼接“最新摘要、保留原文和本轮消息”。
- 估算上下文 token，达到阈值后单独调用模型生成或续写摘要，保留最近原文。
- 保留必要工具调用与结果，去掉推理正文并缩减较大的工具往来。
- 只在完整轮次边界切分；摘要为空或失败时保留原有上下文，不用空摘要替换历史。

这些是应用自己承担的历史选择与压缩。原始聊天仍保存在数据库；压缩改变的是下一次模型输入，不删除用户可以查看的消息。当前预算默认估算 200,000 token；后续应按服务商和模型的实际窗口、系统指令、工具定义及输出预留核对，不能将固定默认值用于所有自定义模型。

### Codex 与实时语音分别处理

本机 Codex 模式通过 `app-server` 的 `thread/start`、`thread/resume` 与 `turn/start` 延续线程；线程上下文由 Codex 管理，应用仍保存界面历史、业务状态、执行审计与范围约束。它不走上述 `prepareContext` 摘要路径。改造应用 API 不等于替换 Codex 内部协议。

实时语音前端使用阿里云的实时会话协议；需要业务查询或修改时委派给 [realtime/jobs.ts](../src/lib/realtime/jobs.ts)，再进入共用 `runChat`。API 演进必须验证这条委派链路，不能把实时语音连接直接当作 Chat Completions 或 Responses。

## Responses API 的价值与适用条件

OpenAI 官方建议新项目优先使用 Responses，同时继续支持 Chat Completions。本项目可逐条流程试点，先核实所选服务商、模型、SDK 适配器支持的能力。

| 事项 | 当前 Chat Completions 路径 | OpenAI Responses 可提供的能力 | 本项目仍须承担 |
| --- | --- | --- | --- |
| 多轮上下文 | 应用每轮组织消息与工具历史 | 可选 `previous_response_id` 串联，或 Conversations 持久会话；也支持自行传递输入输出 Items | 本机消息、界面分页、附件归属、不同会话隔离和恢复映射 |
| 压缩 | 应用触发模型生成可读摘要 | 可配置服务端 `context_management` 和 `compact_threshold`；也可显式调用 `/responses/compact` | 支持性检测、阈值和策略、压缩产物保存及失败处理 |
| 工具与推理状态 | 应用和 AI SDK 管理工具循环，跨轮保存经过整理的结果 | 类型化的消息、推理、函数调用和输出 Items，可保留相应续接状态 | 平台自定义业务工具执行、授权、审计、事务及去重 |
| 成本 | 随选入的上下文和模型计费 | 服务端续接减少客户端重复传输；压缩可减少后续模型输入 | 统计实际用量；仅传前一响应 ID 不等于历史 token 免费 |
| 多服务商 | 当前兼容接口路径可复用 | 接口外形相似不代表会话、压缩、工具及留存能力相同 | 按服务商与模型验证，保留未支持能力时的可用路径 |

### 使用 Responses 后仍要做的事

“服务端记住上下文”“压缩模型窗口”“保存完整产品历史”是三个不同职责。只改成 `/responses` 不会自动获得无限记忆，也不会补齐历史附件工具、资料引用或语义检索。服务端压缩需要明确配置或调用，压缩产物是不可直接阅读的状态，不能替代本机原文与可核验资料。

OpenAI 的响应对象默认保存 30 天，可设置 `store:false` 禁用响应对象存储；Conversations 中的对象和 Items 不采用同一 30 天 TTL。选用服务端会话前应明确产品的保存、删除、备份与迁移方式；`store:false` 不应被解释为所有日志或数据留存政策均已改变。使用 `previous_response_id` 时，链中的历史输入仍计入输入 token 计费。

Responses 不是现有接口的简单地址替换。需要适配类型化流式事件，保留工具调用与结果的对应 ID，以及所需的推理等输出 Items。切换服务商或密钥后，不能假设原响应 ID 或不透明压缩产物可移植；本机历史必须保留以支持明确的恢复策略。

### 第四阶段 独立接口试点

- [ ] **D1 建立能力清单。** 区分服务商、模型、Chat Completions、Responses、服务端续接和压缩支持；原 API 路径与 Codex 路径保持可用。
- [ ] **D2 隔离验证 Responses。** 先用合成资料验证文字、工具多轮、流式输出、线程续接和两种压缩方式中实际需要的方案。不以私人版凭据或数据作为开源测试配置。付费调用与真实资料出站按当次授权执行。
- [ ] **D3 比较并决定采用范围。** 尽可能使用同模型、同工具、同资料与问题，比较正确性、工具成功率、首段时间、整轮耗时、token 与费用；跨模型比较不能将全部差异归因于接口。
- [ ] **D4 验证产品恢复。** 保存响应或会话映射和必要 Items；验证重启、超时、取消、ID 不可用、配置更换、删除及备份恢复。网络重试不能重复写业务，切换后不能悄悄重放旧请求。

建议先完成第一至第三阶段，再根据实际收益确定 Responses 的采用范围。若后续主力使用 OpenAI 且需要原生连续推理和压缩，Responses 值得优先试点；对于现有多服务商桌面应用，保留兼容路径有直接价值。

## 实施与交付约定

- 每次开工先核对本文件基线与实际代码；已有任务浮层、后台轮次、消息分页和摘要能力按增量补齐。
- 共用资料与权限层服务于 API、Codex 和语音委派，界面语言继续支持中英文。私人版固定用户、路径、端口及运维方式不直接搬入。
- 新工具须验证已有 Codex 线程是否识别更新后的 schema。不能仅修改注册列表后假设旧线程自动获得新工具，也不能为更新工具默认清空聊天。
- 可能改变数据库结构或资料读取范围时，先设计迁移、备份和恢复验证。读写权限分开；资料和邮件内容始终视为数据，不产生用户操作授权。
- 验证按改动范围选择现有测试和必要新用例；使用隔离库与合成数据。保留旧任务要求、历史、文件与用户配置，完成实际桌面包验收后再标记交付。
- 一个完整逻辑改动完成验证后提交并推送；打包、安装和发布记录分别说明。发布包检查空模板库、不带账号令牌或模型密钥。
