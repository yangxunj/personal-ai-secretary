# DSH 试验总结与后续方向

记录日期：2026-11-13。本记录总结个人 AI 秘书项目对 DeepSeek Harness（DSH）的阶段性试验，以及回到自有 Agent 平台后的接续方向。结论针对本次验证版本和范围，不代表其他 DSH 版本或客户端已有相同行为。

## 阶段决定

- 近期工作重心回到**自己的秘书平台**，逐步提炼可复用的 Agent 底座和业务模块，支持将来为不同客户构建垂直 Agent。秘书平台是底座的第一个应用；现有代码还不是完整的通用 Agent 生产框架。
- DSH 作为可选生态和集成渠道保留，现有知识幻灯片插件、试验代码和记录继续留存。暂停把试验侧栏接入日常 DSH，不进行数据迁移或清理。
- 以后如有客户使用 DSH，可评估提供垂直插件或通过受控接口连接秘书平台；DSH 能否直接作为秘书平台可替换的 Agent 后端**尚未验证**。

## 试验想回答什么

1. 一个 DSH 插件能否让 AI 创建幻灯片，并在 DSH 中打开自己的页面？
2. 插件能否使用本地持久数据，让 AI 写入后页面读取？
3. 能否复用秘书平台的导航和幻灯片阅读器，把 DSH 界面做得更接近秘书平台？
4. 插件及界面做法是否适合成为长期多客户 Agent 平台的基础？

## 成果和验收边界

| 事项 | 结果 | 证据与限制 |
| --- | --- | --- |
| 幻灯片插件 | AI 可创建、列出和读取 Markdown 幻灯片，DSH 侧栏可打开作品页面 | 用户确认 `0.2.1` 在日常桌面 DSH 中安装和测试通过；该版本有自己的页面入口，不代表整个 DSH 侧栏被插件替换 |
| 复用秘书 UI | `0.3.0` 的独立“秘书界面试验”直接使用秘书导航组件和 Marp 阅读器 | 用户确认该版本测试通过。它保留 DSH 原侧栏，因此有两层侧栏；其他秘书栏目未接入 |
| 插件依赖 | 在隔离 DSH `0.2.2-rc.2` 中，旧版依赖组合曾使新会话初始化报告重复 persona；移除一组 DSH 内部依赖后，新会话可初始化 | `0.3.1` 保留参数及业务数据校验；隔离 Web 中真实模型成功调用工具、创建作品并在页面读取。具体哪个依赖是根因未确定；用户日常桌面 `0.3.1` 的真实模型调用尚无单独验收记录 |
| 单侧栏 | 在隔离 Web 和真实 Windows DSH 桌面窗口中，复用秘书导航并保留 DSH 会话、设置和插件入口 | 用户确认独立桌面试验界面改动生效、体验没有明显问题；自动检查覆盖幻灯片读取/翻页、侧栏收起展开、设置及恢复。用户反馈未逐项说明独立桌面中的真实模型对话，不能据此断言已完成该项验收 |
| 数据保留 | 隔离配置中恢复默认侧栏，再重新启用试验后，测试会话和作品仍可访问 | 验证对象是独立测试数据；不等同于已在日常 DSH 上完成迁移或恢复验收 |
| 安卓 DSH Go | 早期准备了包含原生面板声明的试验插件 | 用户后来明确要求优先 PC；本阶段未验证 DSH Go 新界面、手机实机或跨设备同步。手机 DSH Go 是独立项目，不是 DSH 桌面验证的自动延伸 |

补充：在 `0.3.1` 轻依赖隔离 Web 回归中，真实模型创建的测试作品已在 DSH 幻灯片列表中找到。用户使用独立桌面试验时说“测试了一下没什么问题，看起来这次改动是生效的”，这里按**界面生效的用户确认**记录，不推断未明确报告的测试细节。

## 关键技术认识

### 普通插件与主界面改造是两回事

- 普通 DSH 插件可以注册 `sidebar.panellist` 入口和 `main` 页面，也可以提供 Agent 工具。知识幻灯片插件就是这种形式；插件包的 Host 代码负责工具和存储，客户端负责页面。
- 单侧栏不是一个普通插件的开关。简单禁用 DSH 原侧栏会影响工作区/会话列表；同时声明同名插槽会冲突；仅按优先级覆盖而不拥有子插槽，会因无法渲染子插槽而回退。细节见 [侧栏试验记录](../experiments/dsh-slides/research/sidebar-probe/README.md)。
- 最终原型读取本机 `0.2.2-rc.2` 的 DSH 侧栏组件，确认 SHA-256 后生成一份修改后的组件包，把秘书的 `SideNavView` 编进去，并保留原会话、设置等组件。**这不是 DSH 稳定公开的完整侧栏替换接口**；DSH 更新后内部实现可能变化，不能直接假设继续兼容。
- 试验启动前检查原组件版本和哈希，也检查桌面侧栏包完整性；不匹配时停止。恢复时要检查实际目录联接：曾出现依赖记录已移除但 pnpm 联接仍存在、仍加载试验侧栏的情况，后续恢复流程已针对专用试验链接修正并复验。

### 数据和代码复用的边界

- 插件的幻灯片由 [store.js](../experiments/dsh-slides/lib/store.js) 保存到 `DSH_HOME/secretary-slides-pilot`，使用独立 JSON 文件保存 Markdown 和元数据；它**不连接秘书平台数据库**。同一份插件代码可适配多个宿主，不意味着不同设备或不同 DSH_HOME 自动共享或同步数据。
- 插件可与秘书平台共享校验规则和 React 组件；这次复用了 [幻灯片契约](../src/lib/slides/contracts.ts)、[阅读器](../src/components/slides/SlideViewer.tsx)及 [导航组件](../src/components/navigation/shared/SideNavView.tsx)。DSH 外壳、样式适配、数据接口和平台桥接仍有独立代码；不能称整个网页、Windows、安卓和 DSH 已完全共用。
- 如果未来需要 DSH 与秘书平台共用客户业务数据，应先设计经认证与权限控制的数据服务或受控桥接，确定事务、并发、审计、升级、离线和备份策略；不可把两套存储简单视为同一数据库。
- 独立桌面试验使用独立 DSH_HOME、Electron 用户数据目录和默认工作区；用户主动选择其他工作区时，DSH 的访问范围仍以所选目录和权限配置为准。日常 DSH 和隔离试验的数据不会自动合并。

### 可借鉴的插件设计

用户提供的归藏设计和自媒体工作台都在 DSH 主区域提供各自的业务页面，并使用自己的本地数据或作品索引；源码阅读未发现它们解决了本项目要替换的全局侧栏问题。可借鉴轻依赖、业务数据与界面共用、工具输入校验、作品登记、按容器宽度调整布局等做法。两个项目许可不同，若将来复制具体代码，应先确认对应文件许可；本次只是阅读和分析。详见 [插件参考分析](../experiments/dsh-slides/research/plugin-reference.md)。

## 相对自有平台的取舍

DSH 的现成 Agent、插件机制和生态适合快速构建垂直插件，也适合客户已经采用 DSH 的交付场景。但把完整秘书产品建立在其上，需要另外解决多栏目业务数据、产品界面、安卓体验、版本升级以及客户定制的持续维护；深度定制全局 UI 会增加跟随上游改动的成本。

自有秘书平台已具备多栏目数据模型、Agent 工具和网页/Windows 界面，安卓也已复用部分业务规则与组件；产品界面、数据与客户部署方式更可控。代价是核心 Agent、扩展接口、适配和维护由我们承担。两条路线并非互斥：**自有平台做产品和业务核心，DSH 插件按需要作为可选渠道**；后续应通过真实场景验证，而非现在承诺所有能力无缝互换。

## 回到自有平台后的工作起点

1. 先核实现有对话、待办、任务专属对话、栏目配置与各端实现及验收状态，保留成熟 PC 和已有数据，区分用户实机确认、自动测试和待验证事项。
2. 以待办、知识幻灯片和后续不同客户场景为候选，梳理模块应声明的数据契约、工具、导航、启停、权限和迁移。只读核对显示：当前共享模块注册表只声明待办与幻灯片，实际由安卓试点使用；网页/Windows 的可配置栏目另有数据与服务设计，不能说所有栏目已经使用同一个插件框架。安卓栏目开关的用户验收范围见 [安卓栏目管理验收](安卓栏目管理验收.md)。
3. 对照既有 [可配置栏目实施计划](可配置栏目实施计划.md) 和 [安卓与多端共用路线](安卓与多端共用路线.md)，先确定小范围可验证的通用边界，再决定具体实施；不因为 DSH 试验结束而自动重构所有栏目或发布安装包。
